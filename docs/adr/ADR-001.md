# ADR-001: اعتماد المصادقة على Sanctum مع Role-Based Authorization

- Status: Accepted
- Date: 2026-10-04

## Context

النظام يتضمن ثلاثة أدوار تشغيلية رئيسية:
- Dispatcher
- Technician
- Admin

ويجب حماية الوصول إلى API بشكل واضح، لأن كل دور له صلاحيات مختلفة:
- Dispatcher/Admin يمكنهما إنشاء وعرض الطلبات، وتعيين الفنيين، ومتابعة الأداء.
- Technician يفتح الطلبات المسندة إليه فقط، ويمكنه تحديث الحالات وتقديم التقارير.
- Admin يحتاج إلى رؤية بيانات الإدارة والإحصاءات.

كما أن المشروع يستخدم Laravel 11 ومتطلبات العمل تدفع نحو API RESTful مع مصادقة مستخدمين، دون تعقيد إضافي في طبقة الهوية.

## Decision

نختار اعتماد Laravel Sanctum كحل مصادقة رئيسي، مع سياسة صلاحيات تعتمد على الأدوار (`role`) في جدول `users`، وباستخدام Policies في Laravel للتحقق من صلاحية كل مستخدم حسب المورد.

### تفاصيل القرار
1. كل مستخدم لديه `role` واحد من: `admin`, `dispatcher`, `technician`.
2. عند تسجيل الدخول يتم إصدار Access Token عبر Sanctum.
3. جميع endpoints الخاصة بالطلبات، التقارير، والموظفين محمية بـ `auth:sanctum`.
4. يتم استدعاء `Policy` عند العمليات الحساسة مثل:
   - إنشاء طلب جديد
   - تعيين فني
   - تحديث حالة الطلب
   - إغلاق الطلب
   - عرض سجلات العملاء
5. داخل النموذج، يتم استخدام طرق مثل:
   - `isDispatcher()`
   - `isTechnician()`
   - `isAdmin()`
   - `isOffice()`

## Alternatives considered

### Alternative 1: JWT custom implementation
السبب في الرفض:
- يتطلب كتابة طبقة مصادقة إضافية من الصفر.
- زيادة التعقيد في تكامل Laravel وRefresh Tokens وValidation.
- لا يلائم نمط المشروع التعليمي والعملي الحالي في Laravel كما أن Sanctum أسهل وأبسط.

### Alternative 2: RBAC خارجي / separate auth service
السبب في الرفض:
- غير مناسب لنسخة MVP الحالية.
- يتطلب infra إضافية، إعدادات متعددة، وتعقيد في النشر لا يتناسب مع نطاق المشروع.
- يؤخر الوصول إلى القيم التشغيلية الأساسية.

### Alternative 3: استخدام صلاحيات ثابتة فقط حسب endpoint (بدون Policies)
السبب في الرفض:
- لا يسمح بنموذج صلاحيات دقيقة حسب المورد.
- يصعب التعامل مع السيناريوهات مثل:
  - technician يرى فقط طلباته
  - dispatcher يرؤية كل الطلبات
  - admin يرى الإحصاءات والطلبات المعلقة
- يعرض النظام لخطر واسع للانتهاكات في المستقبل.

## Consequences

### Positive
- تنفيذ سريع ومناسب لقيود Laravel 11.
- دعم بسيط جدًا للمصادقة والوصول.
- توافق قوي مع المستودع الحالي، حيث توجد بالفعل مستخدمون بأدوار مختلفة.
- سهولة التوسع عند إضافة أدوار جديدة في المستقبل.

### Negative
- لا يوجد دعم متقدم للـ RBAC المعقد عبر وحدات/صلاحيات متعددة في هذا القرار.
- يتطلب تنظيم جيد للـ Policies في كل كيان لضمان قراءة واضحة للصلاحيات.
- عند دخول أكثر من دور جديد، يحتاج المشروع إلى تحديث السياسة والحقول في `users`.

## Implementation notes

اتجاه التنفيذ المقترح:
- `AuthController` يقوم بإنشاء الـ token عند login.
- `MaintenanceRequestPolicy` يتحكم في `view`, `assign`, `updateStatus`, `report`.
- `User` model يحتوي على طرق `isDispatcher()`, `isTechnician()`, `isAdmin()`.
- جميع واجهات API تستدعي `auth:sanctum` ثم تُحقق السياسة على مستوى controller أو request.

## Result

تم اختيار نموذج مصادقة مبني على Sanctum + Policies + Role-based authorization كحل عملي ومناسب للـ MVP، ويحقق متطلبات الأمان الأساسية دون تعقيد غير ضروري.
